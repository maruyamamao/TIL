# システム開発
→人の手で行っていたものをコンピュータに置きかえて効率アップをはかる

## 開発の流れ
企画プロセス → 要件定義プロセス → 開発プロセス → 運用プロセス → 保守プロセス

- **要件**：要求→(要求)仕様→要件、仕様と要求を両方満たすためのやることの一覧
- **RFI**：情報提供依頼書
- **RFP**：提案依頼書

## 非機能要件
→機能やシステムと関係ないこと、可用性など

|項目|説明|要件例|
|-|-|-|
|可用性|システムサービスを継続的に利用可能とするための要求|・運用スケジュール<br>・障害、災害時における稼働目標|
|性能・拡張性|システムの性能、将来のシステム拡張に関する要求|・業務量、今後の増加見積もり<br>・システム化対象業務の特性|
|運用・保守性|システムの運用と捕手のサービスに関する要求|・運用中に求められるシステム稼働レベル<br>・問題発生時の対応レベル|
|移行性|現行システム資産の移行に関する要求|・新システムへの移行期間、移行方法<br>・移動対象資産の種類及び以降量|
|セキュリティ|情報システムの安全性の確保に関する要求|・利用制限<br>・不正アクセスの防止|
|システム環境<br>エコロジー|システムの設置環境やエコロジーの関する要求|・耐震、地震、重量、空洞などシステム環境に関する事項<br>・CO₂排出量や消費エネルギーなどエコロジーに関する事項|


**外部設計**：システムを「利用者から見た」設計を行うこと、利用者が実際に手に触れる部分、画面レイアウトなど、これを承認しないと内部設計に移動できない
**内部設計**：システムを「開発者から見た」設計を行うこと、実装方法や物理データ設計など、利用者がふれることのない部分の設計

## レビューの手法
※デザインとはシステム開発時に使う**設計**のこと
**デザインレビュー**：設計段階で作成した仕様書に対して不備がないか確認するためのレビュー、設計の妥当性を検証する
**コードレビュー**：作成したプログラムに不備がないか確認するためにソースコードを対象として行われるレビュー

※関係者 = 利害関係者(ステークホルダ)
**ウォークスルー**：問題の早期発見が目的、開発者が主体となって複数の関係者とプログラムや設計書のレビューを行う手法
**インスペクション**：進行役として第三者であるモデレータがレビュー責任者を務めてレビューを実施する手法
**ラウンドロビン**：参加者全員が持ち回りでレビュー責任者を務めながらレビューを行う手法

## 開発手法
**XR(エクストリーム・プログラミング)**
**ペアプログラミング**：2人1組でプログラミングを行い、品質向上や知識の共有のために行われる
**リファクタリング**：内部のコードだけ改善、外部の動作は変更しない、テストが大事
**リバースエンジニアリング**：すでにあるソフトウェアから解析し新しいものを作る

## テスト
**トップダウンテスト**：上位モジュールの上から順にテスト行う、スタブ
**ボトムアップテスト**：下位モジュールの下から順にテストする

## システムの信頼性と稼働率
**MTBF**：平均故障間隔時間
**MTTR**:平均修理時間
```
       平均故障間隔                    MTBF
＿＿＿＿＿＿＿＿＿＿＿＿＿＿    ＝  ＿＿＿＿＿＿＿
平均故障間隔 ＋ 平均修理時間        MTBF ＋ MTTR
```

**稼働率**：動いている時間 ÷ 全部の時間

**直列接続**：すべてが動いているときしか動かない
```
直列システムの稼働率 = 稼働率A × 稼働率B
```
**並列接続**：すべてが止まっているときだけ止まる
```
故障率 = 1 - 稼働率
全体の故障率 = 故障率A × 故障率B
```
**フォールトトレラント**：壊れても大丈夫なように対策する
**フォールトアボイダンス**：壊れないように対策をする
